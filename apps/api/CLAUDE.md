# apps/api — NestJS

Общие правила репозитория — в `../../CLAUDE.md`.

## Команды (из `apps/api` или `pnpm --filter api ...`)

- `dev` — запуск с watch на порту 3001 (`PORT` переопределяет)
- `build`, `start:prod`
- `lint` (oxlint с проверкой типов), `lint:fix`, `typecheck`
- `db:migrate` (создать миграцию в dev-БД), `db:deploy` (применить миграции), `db:generate` (сгенерировать Prisma Client; выполняется и в `postinstall`)
- `test` — unit (vitest, `src/**/*.spec.ts`; `passWithNoTests`); `test:e2e` — e2e (`test/*.e2e-spec.ts`)

## Структура и соглашения

- Пакет ESM (`"type": "module"`, `nodenext`): относительные импорты **обязательно с расширением `.js`**, например `'./app.module.js'`.
- Модули по доменам: `auth/`, `users/`, `meetings/`, `meeting-files/`. Контроллер + сервис + DTO + модуль в одной папке. Корневого контроллера нет: `AppModule` только собирает модули (маршрута `GET /` не существует).
- DTO валидируются через `class-validator`; глобальный `ValidationPipe` и CORS подключаются в `src/setup-app.ts` (его же используют e2e-тесты, не дублируйте настройку в `main.ts`).
- Защищённые маршруты: `@UseGuards(JwtAuthGuard)`, текущий пользователь — `req.user` (`AuthRequest`).
- Модуль `auth` построен на CQRS (`@nestjs/cqrs`): контроллер только отправляет сообщения в `CommandBus`/`QueryBus`, вся логика — в обработчиках. Регистрация — команда `RegisterUserCommand` (`auth/commands/`), логин — запрос `LoginQuery` (`auth/queries/`, он не меняет состояние). Новые операции добавляйте как пару `*.command.ts`/`*.handler.ts` (или `*.query.ts`/`*.handler.ts`) и регистрируйте обработчик в `providers` модуля. Подробнее — в `docs/cqrs.md`.
- Пароли хешируются в `auth/password.ts` (асинхронный scrypt; `verifyPassword` не бросает на повреждённом хеше, `DUMMY_HASH` выравнивает время `login` для несуществующего email), JWT выдаёт `AuthTokenService`. Безопасность: `JwtAuthGuard` проверяет подпись (только HS256), затем читает пользователя из БД — удалённый пользователь или несовпавшая `tokenVersion` (`User.tokenVersion`, растёт при смене пароля) → 401; payload токена — `sub` и `tv`, email берётся из БД и всегда актуален. Секрет — `getJwtSecret()` (`auth/jwt-secret.ts`). Лимиты запросов — `@nestjs/throttler`: глобальный `ThrottlerGuard` (`RATE_LIMIT`, 300/мин на IP) и строгий `AUTH_THROTTLE` (`AUTH_RATE_LIMIT`, 10/мин) на `register`, `login`, `PATCH /users/me`, `PUT /users/me/password`, `DELETE /users/me`; сверх лимита — 429. `setup-app.ts` подключает `helmet()`, CORS и `ValidationPipe` (`whitelist` + `forbidNonWhitelisted`). Пароли ≤128 символов, email ≤254.
- ORM — Prisma 7 (`prisma/schema.prisma`, конфиг `prisma.config.ts`, драйвер-адаптер `@prisma/adapter-pg`). Клиент генерируется в `src/generated/prisma` (в git не хранится); импортируйте из `../generated/prisma/client.js`. `PrismaService` (глобальный `PrismaModule`) — единственная точка доступа к БД.
- `UsersService` работает через Prisma; уникальность email обеспечивает БД (ошибка `P2002` превращается в 409 в `RegisterUserHandler` и в `UsersService.updateProfile`). Хеш пароля наружу не отдаётся — используйте `toProfile()` / `UserProfile` (включает `hasAvatar` и `avatarUpdatedAt` — для сброса кэша; запросы пользователя должны брать `include: WITH_AVATAR`). `DELETE /users/me` после удаления записи удаляет и файл аватара с диска.
- Эндпоинты `users` (все под `JwtAuthGuard`, обычные контроллер+сервис без CQRS): `GET /users?search=` (обязателен, ≥3 символов, иначе 400; по части имени или **точному** email; отдаёт `PublicProfile` без email, до 20 записей), `GET /users/me`, `PATCH /users/me` (`name`, `email`; пустое имя сбрасывает; для смены email нужен `password` — текущий пароль, иначе 400), `PUT /users/me/password` (`currentPassword`, `newPassword`; 200 + `AuthResult`: старые токены отозваны, в ответе новый), `DELETE /users/me` (`password` в теле; 204), `GET /users/:id` (UUID, иначе 400; 404 если нет; только `PublicProfile`: `id`, `name`, `hasAvatar`, `avatarUpdatedAt`, без email). Тесты — `test/users.e2e-spec.ts`.
- `MeetingsService` пока держит данные в памяти — при переходе на БД менять нужно только его. Лимит — `MAX_MEETINGS_PER_USER` (1000), сверх него 403.
- После изменения `schema.prisma` создайте миграцию: `pnpm --filter api db:migrate -- --name <имя>`.
- e2e-тесты работают с отдельной БД `video_meetings_test` (`test/test-database.ts`, `TEST_DATABASE_URL` переопределяет); `test/global-setup.ts` применяет к ней миграции, файлы идут последовательно, а таблицу `users` каждый тест очищает сам.
- Эндпоинты `meetings` (все под `JwtAuthGuard`): `POST /meetings` (`title` обязателен; `date` ISO 8601 и `participants` — массив строк необязательны), `GET /meetings`, `GET /meetings/:id` (404 для несуществующей и чужой встречи). Во всех ответах есть `hasFile` (boolean): `MeetingsController` считает его одним запросом к `meeting_files` через `PrismaService` (не через `MeetingFilesService`: `MeetingFilesModule` уже импортирует `MeetingsModule`, иначе цикл). Тесты — `test/meetings.e2e-spec.ts`.
- Файл встречи (`meeting-files/`, обычные контроллер+сервис, без CQRS): `POST /meetings/:id/file` (multipart, поле `file`; 201 + метаданные, 409 если файл уже есть, 400 без файла) `GET /meetings/:id/file` (метаданные: `id`, `meetingId`, `originalName`, `mimeType`, `size`, `status` = `UPLOADED`, `uploadedAt`, `transcriptionStatus`; 404 если файла нет), `GET /meetings/:id/file/download` (потоковая отдача: `Content-Type` из БД, `Content-Length`, `Content-Disposition: attachment` с `filename` (ASCII-запас) и `filename*` (UTF-8) из `content-disposition.ts`, `X-Content-Type-Options: nosniff`; 404, если записи нет или файл пропал с диска), `PUT /meetings/:id/file` (замена, те же multipart-поле и валидация, что у `POST`; 200 + метаданные с прежним `id`; если файла не было — ведёт себя как `POST`; сначала обновляются метаданные, затем удаляется старый файл с диска, при ошибке новый файл удаляется, а старый и его метаданные не меняются; обновление условное по старому `storageKey`, поэтому проигравшая параллельная замена получает 409 и удаляет только свой файл) и `DELETE /meetings/:id/file` (204; удаляет запись и файл с диска; 404, если файла нет; сбой удаления с диска только логируется). Порядок: `JwtAuthGuard` → `MeetingOwnerGuard` (404 для чужой/несуществующей встречи до чтения тела) → для `POST` `MeetingFileAbsentGuard` (409, если файл уже есть, до чтения тела) → `FileInterceptor` с собственным `MeetingFileStorage` (поток в `<FILES_STORAGE_DIR>/tmp/<uuid>`, затем атомарный `rename` в `files/<uuid>`; имя на диске генерирует сервер, исходное имя — только в БД). В БД (`MeetingFile`, таблица `meeting_files`) хранится относительный `storageKey`, наружу он не отдаётся. `meetingId` без FK, т.к. встречи в памяти. Квота: `MeetingFileQuotaGuard` (для `POST` и `PUT`, до чтения тела) отклоняет 413 загрузку, после которой сумма файлов пользователя превысит 5 ГБ (`USER_FILES_QUOTA` в байтах; размер — по `Content-Length`, файл заменяемой встречи не считается). Валидация (фаза 2): допустимы mp4, mov, webm, mp3, m4a, wav, pdf, docx, pptx, txt, vtt, srt (таблица `ALLOWED_TYPES` в `meeting-file.types.ts`; для mp4 допустим и `video/x-m4v` — бренды `M4V `/`M4VH`); расширение неизвестно → 415 до записи на диск. Тип проверяется по содержимому в `meeting-file.validator.ts` (`file-type`; для docx/pptx дополнительно ищется `word/document.xml`/`ppt/presentation.xml` в центральном каталоге zip; текст — без NUL-байтов, кроме UTF-16 с BOM): этап 1 — по первым 4100 байтам прямо в потоке (неопределённый результат не отклоняет, решает этап 2; отклоняется только заведомо другой тип), этап 2 — по готовому tmp-файлу до `rename`; несовпадение с расширением → 415. В БД пишется MIME, определённый сервером (клиентский игнорируется), и очищенное имя (`sanitizeFileName`: без путей и управляющих символов, ≤255). Лимит 500 МБ (`MEETING_FILE_MAX_SIZE` в байтах переопределяет, нужно для тестов): `MeetingFileSizeGuard` (и для `POST`, и для `PUT`) по `Content-Length` до чтения тела, счётчик в `MeetingFileStorage` и `limits.fileSize` multer → 413; пустой файл → 400. При любой ошибке/обрыве tmp-файл удаляется (после закрытия потока записи, иначе незавершённое открытие создаст файл уже после `rm`), запись в БД не создаётся. Запись в storage сделана вручную (не `pipeline`) и читает поток через `iterator({ destroyOnReturn: false })`: иначе multer принимает AbortError вместо нашей ошибки. `MeetingFileUploadFilter` переводит английские сообщения multer на русский. `requestTimeout` HTTP-сервера — 30 минут, `headersTimeout` — 15 с (`server-config.ts`, только в `main.ts`). Очистка сирот (`MeetingFilesCleanupService`, `OnApplicationBootstrap`, до `listen`): встречи в памяти пропадают при перезапуске, поэтому на старте удаляются записи `MeetingFile` без встречи (с их файлами), файлы в `files/` без записи в БД и хвосты `tmp/`; трогаются только файлы с именем-uuid, сбой очистки только логируется и запуск не прерывает. Тесты — `src/meeting-files/*.spec.ts`, `src/meetings/meetings.controller.spec.ts` и `test/meeting-files.e2e-spec.ts`; образцы файлов собираются в коде (`test/sample-files.ts`) (хранилище e2e — временная папка, `test/test-storage.ts`).
- Транскрибация MP3/MP4 (`meeting-files/transcription/`, локальный Whisper). Модель `MeetingFileTranscription` (таблица `meeting_file_transcriptions`: `meetingFileId` уникален, FK на `meeting_files` с `ON DELETE CASCADE`; `status` = `QUEUED`/`PROCESSING`/`DONE`/`FAILED`, `text`, `error`, `completedAt`); `MeetingFile.status` остаётся `UPLOADED`. Задача создаётся в `MeetingFilesService.create/replace` (`TranscriptionQueue.enqueue`) только если сервер определил MIME как `video/mp4` или `audio/mpeg`; для остальных форматов задачи нет, а при замене на такой формат прежняя запись удаляется. Сбой постановки в очередь не отменяет загрузку. `TranscriptionQueue` — последовательная очередь в процессе API (один файл за раз, FIFO; в памяти только порядок, состояние в БД). `TranscriptionRunner` — абстрактный класс-токен DI (в e2e подменяется через `overrideProvider`, см. `test/fake-transcription-runner.ts`); боевой `WhisperTranscriptionRunner` через `execFile` (без блокировки Node) гоняет `ffmpeg` (mono 16 кГц wav во временный каталог) и `whisper`, ошибки — `TranscriptionError` с русским сообщением (ffmpeg/Whisper недоступны, файл повреждён). Таймаут (`TRANSCRIPTION_TIMEOUT_MS`) и отмена убивают процесс через `AbortSignal` (`SIGKILL`). Результат пишется условным `updateMany` (статус `PROCESSING` и прежний `storageKey` файла), поэтому ответ устаревшей задачи после замены или удаления файла игнорируется; `enqueue` и `DELETE /meetings/:id/file` прерывают идущую задачу файла (`cancel`). Восстановление: `MeetingFilesCleanupService` после очистки сирот вызывает `TranscriptionQueue.recover()` — «В процессе» возвращается в «В очереди», задачи ставятся в порядке `uploadedAt`; задачи удалённых файлов уходят каскадом. Пока встречи живут в памяти, после рестарта все файлы удаляются очисткой, так что восстановление срабатывает только после переноса встреч в БД. Эндпоинты (`JwtAuthGuard` → `MeetingOwnerGuard`): `GET /meetings/:id/file/transcription` (`status`, `text`, `error`, `completedAt`; 404, если файла или задачи нет), `GET /meetings/:id/file/transcription/download` (`.txt`, `text/plain; charset=utf-8`, `Content-Disposition: attachment` с именем исходного файла без расширения + `.txt`, `nosniff`; 409, пока статус не «Готово»), `POST /meetings/:id/file/transcription/retry` (200 + статус; 409, если статус не `FAILED`; кроме общего `RATE_LIMIT` — `RETRY_THROTTLE`, `TRANSCRIPTION_RETRY_RATE_LIMIT`, 5/мин). Тесты — `transcription/*.spec.ts`, `test/meeting-file-transcription.e2e-spec.ts`.
- Сообщения об ошибках для пользователя — на русском.

## Окружение

- `PORT` — порт API (по умолчанию 3001)
- `DATABASE_URL` — строка подключения к Postgres (по умолчанию локальная БД из Docker Compose; при `NODE_ENV=production` обязательна)
- `JWT_SECRET` — секрет токена (вне production есть dev-значение; при `NODE_ENV=production` обязателен, ≥32 символов, иначе API не стартует)
- `RATE_LIMIT` — общий лимит запросов с одного IP в минуту (по умолчанию 300); `AUTH_RATE_LIMIT` — лимит для входа, регистрации и операций с паролем (по умолчанию 10); e2e выставляют большие значения в `vitest.config.e2e.ts`
- `USER_FILES_QUOTA` — квота файлов встреч на пользователя в байтах (по умолчанию 5 ГБ)
- `FILES_STORAGE_DIR` — каталог файлов встреч (по умолчанию `./storage` относительно `apps/api`, в `.gitignore`)
- `AVATARS_STORAGE_DIR` — каталог аватаров пользователей (по умолчанию `./storage/avatars` относительно `apps/api`; отдельно от `files/` и `tmp/`, чтобы очистка сирот встреч их не трогала). Модель `UserAvatar` (таблица `user_avatars`: `userId` уникален, FK на `users` с `ON DELETE CASCADE`, `mimeType`, `size`, `storageKey`, `updatedAt`). Эндпоинты аватара (`avatars/`, все под `JwtAuthGuard`): `PUT /users/me/avatar` (multipart, поле `file`; JPEG/PNG/WebP до 5 МБ; 200 + `mimeType`, `size`, `updatedAt`), `GET /users/:id/avatar` (любой авторизованный; UUID, иначе 400; 404, если аватара нет или файл пропал с диска; `Content-Type` из БД, `nosniff`, `Cache-Control: private, no-cache`), `DELETE /users/me/avatar` (204; 404, если аватара нет). Файл целиком в памяти (`memoryStorage`, лимит multer + `AvatarSizeGuard` по `Content-Length` → 413), тип по содержимому в `avatar.validator.ts` (`file-type`, иначе 415), пустой файл → 400. При замене новый файл пишется под новым uuid, затем `upsert`, затем удаляется старый; при сбое новый файл удаляется, прежний остаётся. Тесты — `src/avatars/*.spec.ts`, `test/avatars.e2e-spec.ts` (каталог e2e — `TEST_AVATARS_DIR`)
- `MEETING_FILE_MAX_SIZE` — лимит размера файла встречи в байтах (по умолчанию 524288000 = 500 МБ, максимум 2147483647 — колонка `size` типа Int)
- `WHISPER_COMMAND` (по умолчанию `whisper`), `FFMPEG_COMMAND` (`ffmpeg`), `WHISPER_MODEL` (`base`), `WHISPER_MODEL_DIR` (каталог с моделью; без него Whisper берёт свой кэш и при первом запуске скачивает модель из сети — скачайте заранее), `TRANSCRIPTION_TIMEOUT_MS` (по умолчанию 2 часа), `TRANSCRIPTION_RETRY_RATE_LIMIT` (повторов в минуту, по умолчанию 5). Установка: `pip install openai-whisper` и `brew install ffmpeg` (или пакетный менеджер ОС); без них задачи завершаются статусом «Ошибка» с сообщением, API не падает
- `WEB_ORIGIN` — разрешённый origin для CORS (по умолчанию `http://localhost:3000`)
