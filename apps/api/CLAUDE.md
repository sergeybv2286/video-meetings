# apps/api — NestJS

Общие правила репозитория — в `../../CLAUDE.md`.

## Команды (из `apps/api` или `pnpm --filter api ...`)

- `dev` — запуск с watch на порту 3001 (`PORT` переопределяет)
- `build`, `start:prod`
- `lint` (oxlint с проверкой типов), `lint:fix`, `typecheck`
- `db:migrate` (создать миграцию в dev-БД), `db:deploy` (применить миграции), `db:generate` (сгенерировать Prisma Client; выполняется и в `postinstall`)
- `test` — unit (vitest, `src/**/*.spec.ts`; `passWithNoTests`); `test:e2e` — e2e (`test/*.e2e-spec.ts`)

## Структура и соглашения

- Пакет ESM (`"type": "module"`, `nodenext`): относительные импорты **обязательно с расширением `.js`**, например `'./app.module.js'`.
- Модули по доменам: `auth/`, `users/`, `meetings/`, `meeting-files/`. Контроллер + сервис + DTO + модуль в одной папке. Корневого контроллера нет: `AppModule` только собирает модули (маршрута `GET /` не существует).
- DTO валидируются через `class-validator`; глобальный `ValidationPipe` и CORS подключаются в `src/setup-app.ts` (его же используют e2e-тесты, не дублируйте настройку в `main.ts`).
- Защищённые маршруты: `@UseGuards(JwtAuthGuard)`, текущий пользователь — `req.user` (`AuthRequest`).
- Модуль `auth` построен на CQRS (`@nestjs/cqrs`): контроллер только отправляет сообщения в `CommandBus`/`QueryBus`, вся логика — в обработчиках. Регистрация — команда `RegisterUserCommand` (`auth/commands/`), логин — запрос `LoginQuery` (`auth/queries/`, он не меняет состояние). Новые операции добавляйте как пару `*.command.ts`/`*.handler.ts` (или `*.query.ts`/`*.handler.ts`) и регистрируйте обработчик в `providers` модуля. Подробнее — в `docs/cqrs.md`.
- Пароли хешируются в `auth/password.ts` (scrypt), JWT выдаёт `AuthTokenService`.
- ORM — Prisma 7 (`prisma/schema.prisma`, конфиг `prisma.config.ts`, драйвер-адаптер `@prisma/adapter-pg`). Клиент генерируется в `src/generated/prisma` (в git не хранится); импортируйте из `../generated/prisma/client.js`. `PrismaService` (глобальный `PrismaModule`) — единственная точка доступа к БД.
- `UsersService` работает через Prisma; уникальность email обеспечивает БД (ошибка `P2002` превращается в 409 в `RegisterUserHandler` и в `UsersService.updateProfile`). Хеш пароля наружу не отдаётся — используйте `toProfile()` / `UserProfile` (включает `hasAvatar` и `avatarUpdatedAt` — для сброса кэша; запросы пользователя должны брать `include: WITH_AVATAR`). `DELETE /users/me` после удаления записи удаляет и файл аватара с диска.
- Эндпоинты `users` (все под `JwtAuthGuard`, обычные контроллер+сервис без CQRS): `GET /users?search=` (поиск по части email/имени, до 20 записей), `GET /users/me`, `PATCH /users/me` (`name`, `email`; пустое имя сбрасывает), `PUT /users/me/password` (`currentPassword`, `newPassword`; 204), `DELETE /users/me` (`password` в теле; 204), `GET /users/:id` (UUID, иначе 400; 404 если нет). Тесты — `test/users.e2e-spec.ts`. JWT хранит email на момент входа, поэтому после смены email `/auth/me` отдаёт старое значение до повторного входа — актуальный профиль в `/users/me`.
- `MeetingsService` пока держит данные в памяти — при переходе на БД менять нужно только его.
- После изменения `schema.prisma` создайте миграцию: `pnpm --filter api db:migrate -- --name <имя>`.
- e2e-тесты работают с отдельной БД `video_meetings_test` (`test/test-database.ts`, `TEST_DATABASE_URL` переопределяет); `test/global-setup.ts` применяет к ней миграции, файлы идут последовательно, а таблицу `users` каждый тест очищает сам.
- Эндпоинты `meetings` (все под `JwtAuthGuard`): `POST /meetings` (`title` обязателен; `date` ISO 8601 и `participants` — массив строк необязательны), `GET /meetings`, `GET /meetings/:id` (404 для несуществующей и чужой встречи). Во всех ответах есть `hasFile` (boolean): `MeetingsController` считает его одним запросом к `meeting_files` через `PrismaService` (не через `MeetingFilesService`: `MeetingFilesModule` уже импортирует `MeetingsModule`, иначе цикл). Тесты — `test/meetings.e2e-spec.ts`.
- Файл встречи (`meeting-files/`, обычные контроллер+сервис, без CQRS): `POST /meetings/:id/file` (multipart, поле `file`; 201 + метаданные, 409 если файл уже есть, 400 без файла) `GET /meetings/:id/file` (метаданные: `id`, `meetingId`, `originalName`, `mimeType`, `size`, `status` = `UPLOADED`, `uploadedAt`; 404 если файла нет), `GET /meetings/:id/file/download` (потоковая отдача: `Content-Type` из БД, `Content-Length`, `Content-Disposition: attachment` с `filename` (ASCII-запас) и `filename*` (UTF-8) из `content-disposition.ts`, `X-Content-Type-Options: nosniff`; 404, если записи нет или файл пропал с диска), `PUT /meetings/:id/file` (замена, те же multipart-поле и валидация, что у `POST`; 200 + метаданные с прежним `id`; если файла не было — ведёт себя как `POST`; сначала обновляются метаданные, затем удаляется старый файл с диска, при ошибке новый файл удаляется, а старый и его метаданные не меняются; обновление условное по старому `storageKey`, поэтому проигравшая параллельная замена получает 409 и удаляет только свой файл) и `DELETE /meetings/:id/file` (204; удаляет запись и файл с диска; 404, если файла нет; сбой удаления с диска только логируется). Порядок: `JwtAuthGuard` → `MeetingOwnerGuard` (404 для чужой/несуществующей встречи до чтения тела) → для `POST` `MeetingFileAbsentGuard` (409, если файл уже есть, до чтения тела) → `FileInterceptor` с собственным `MeetingFileStorage` (поток в `<FILES_STORAGE_DIR>/tmp/<uuid>`, затем атомарный `rename` в `files/<uuid>`; имя на диске генерирует сервер, исходное имя — только в БД). В БД (`MeetingFile`, таблица `meeting_files`) хранится относительный `storageKey`, наружу он не отдаётся. `meetingId` без FK, т.к. встречи в памяти. Валидация (фаза 2): допустимы mp4, mov, webm, mp3, m4a, wav, pdf, docx, pptx, txt, vtt, srt (таблица `ALLOWED_TYPES` в `meeting-file.types.ts`; для mp4 допустим и `video/x-m4v` — бренды `M4V `/`M4VH`); расширение неизвестно → 415 до записи на диск. Тип проверяется по содержимому в `meeting-file.validator.ts` (`file-type`; для docx/pptx дополнительно ищется `word/document.xml`/`ppt/presentation.xml` в центральном каталоге zip; текст — без NUL-байтов, кроме UTF-16 с BOM): этап 1 — по первым 4100 байтам прямо в потоке (неопределённый результат не отклоняет, решает этап 2; отклоняется только заведомо другой тип), этап 2 — по готовому tmp-файлу до `rename`; несовпадение с расширением → 415. В БД пишется MIME, определённый сервером (клиентский игнорируется), и очищенное имя (`sanitizeFileName`: без путей и управляющих символов, ≤255). Лимит 500 МБ (`MEETING_FILE_MAX_SIZE` в байтах переопределяет, нужно для тестов): `MeetingFileSizeGuard` (и для `POST`, и для `PUT`) по `Content-Length` до чтения тела, счётчик в `MeetingFileStorage` и `limits.fileSize` multer → 413; пустой файл → 400. При любой ошибке/обрыве tmp-файл удаляется (после закрытия потока записи, иначе незавершённое открытие создаст файл уже после `rm`), запись в БД не создаётся. Запись в storage сделана вручную (не `pipeline`) и читает поток через `iterator({ destroyOnReturn: false })`: иначе multer принимает AbortError вместо нашей ошибки. `MeetingFileUploadFilter` переводит английские сообщения multer на русский. `requestTimeout` HTTP-сервера — 30 минут (`server-config.ts`, только в `main.ts`). Очистка сирот (`MeetingFilesCleanupService`, `OnApplicationBootstrap`, до `listen`): встречи в памяти пропадают при перезапуске, поэтому на старте удаляются записи `MeetingFile` без встречи (с их файлами), файлы в `files/` без записи в БД и хвосты `tmp/`; трогаются только файлы с именем-uuid, сбой очистки только логируется и запуск не прерывает. Тесты — `src/meeting-files/*.spec.ts`, `src/meetings/meetings.controller.spec.ts` и `test/meeting-files.e2e-spec.ts`; образцы файлов собираются в коде (`test/sample-files.ts`) (хранилище e2e — временная папка, `test/test-storage.ts`).
- Сообщения об ошибках для пользователя — на русском.

## Окружение

- `PORT` — порт API (по умолчанию 3001)
- `DATABASE_URL` — строка подключения к Postgres (по умолчанию локальная БД из Docker Compose)
- `JWT_SECRET` — секрет токена (по умолчанию dev-значение, в проде обязательно задать)
- `FILES_STORAGE_DIR` — каталог файлов встреч (по умолчанию `./storage` относительно `apps/api`, в `.gitignore`)
- `AVATARS_STORAGE_DIR` — каталог аватаров пользователей (по умолчанию `./storage/avatars` относительно `apps/api`; отдельно от `files/` и `tmp/`, чтобы очистка сирот встреч их не трогала). Модель `UserAvatar` (таблица `user_avatars`: `userId` уникален, FK на `users` с `ON DELETE CASCADE`, `mimeType`, `size`, `storageKey`, `updatedAt`). Эндпоинты аватара (`avatars/`, все под `JwtAuthGuard`): `PUT /users/me/avatar` (multipart, поле `file`; JPEG/PNG/WebP до 5 МБ; 200 + `mimeType`, `size`, `updatedAt`), `GET /users/:id/avatar` (любой авторизованный; UUID, иначе 400; 404, если аватара нет или файл пропал с диска; `Content-Type` из БД, `nosniff`, `Cache-Control: private, no-cache`), `DELETE /users/me/avatar` (204; 404, если аватара нет). Файл целиком в памяти (`memoryStorage`, лимит multer + `AvatarSizeGuard` по `Content-Length` → 413), тип по содержимому в `avatar.validator.ts` (`file-type`, иначе 415), пустой файл → 400. При замене новый файл пишется под новым uuid, затем `upsert`, затем удаляется старый; при сбое новый файл удаляется, прежний остаётся. Тесты — `src/avatars/*.spec.ts`, `test/avatars.e2e-spec.ts` (каталог e2e — `TEST_AVATARS_DIR`)
- `MEETING_FILE_MAX_SIZE` — лимит размера файла встречи в байтах (по умолчанию 524288000 = 500 МБ, максимум 2147483647 — колонка `size` типа Int)
- `WEB_ORIGIN` — разрешённый origin для CORS (по умолчанию `http://localhost:3000`)
