# Research: техническая реализация загрузки файла встречи

**План:** `docs/plan-meeting-file-upload.md` · **PRD:** `docs/prd-meeting-file-upload.md`
**Дата:** 2026-10-12

Цель — выбрать оптимальные технические решения для фаз 1–7 плана с учётом текущего стека: NestJS 12 (ESM, Express 5), Prisma 7, Postgres 17, Node 24, Next.js (App Router), HeroUI v3. Часть выводов проверена экспериментально (помечено «проверено»).

## Резюме решений

| Вопрос                     | Решение                                                                                                                                                                   |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Приём multipart            | `FileInterceptor` из `@nestjs/platform-express` (multer 2.4 / busboy 1.6 уже в зависимостях) с **собственным `StorageEngine`**, а не готовым `diskStorage`                |
| Запись на диск             | поток в `<STORAGE>/tmp/<uuid>`, после валидации — атомарный `rename` в `<STORAGE>/files/<uuid>`                                                                           |
| Имя на диске               | только серверный `randomUUID()`, без расширения; исходное имя только в БД                                                                                                 |
| Лимит 500 МБ               | `limits.fileSize` у multer (→ 413) + ранний отказ по `Content-Length` + `limits: { files: 1, fields: 0 }`                                                                 |
| Проверка типа              | двухэтапная: префикс первого чанка + полное определение `file-type` на tmp-файле; для txt/vtt/srt — проверка текста; расширение должно соответствовать определённому типу |
| Согласованность БД и диска | сначала файл на диск, потом запись в БД; при любой ошибке — удаление файла; замена через «новый файл → транзакция в БД → удаление старого»                                |
| Скачивание                 | `StreamableFile` + `Content-Disposition` (RFC 5987); авторизация для браузера — короткоживущая ссылка с токеном (см. §6)                                                  |
| Клиентская загрузка        | `XMLHttpRequest` (нужен `upload.onprogress`; `fetch` прогресс отправки не даёт) напрямую в API                                                                            |
| Сироты                     | очистка при старте API (`OnApplicationBootstrap`), как в плане                                                                                                            |
| Новые зависимости          | для API — нет обязательных (`multer` и `file-type` уже транзитивно есть, их нужно добавить в `apps/api` явно); для web — нет                                              |

## 1. Приём multipart-загрузки

**Варианты**

1. `FileInterceptor` + `multer.diskStorage` — идиоматично для Nest, но `diskStorage` пишет файл целиком и только потом отдаёт управление: валидация по содержимому возможна лишь постфактум, мусор до 500 МБ успевает записаться.
2. `FileInterceptor` + **свой `StorageEngine`** (рекомендуется) — сохраняем всё, что даёт multer (лимиты, обработка обрыва, маппинг ошибок в `PayloadTooLargeException`), но получаем доступ к потоку: можно подсмотреть первый чанк, отклонить файл до записи остальных байт и писать сразу в tmp-путь.
3. Прямое использование `busboy` в контроллере — максимум контроля, но придётся самим делать маппинг ошибок, очистку и тестовые обвязки; выигрыш по сравнению с п. 2 минимален.
4. `memoryStorage` — запрещён PRD (нельзя читать файл целиком в память).

**Как это выглядит в проекте**

- Пакет — ESM, импорты с `.js`. `multer` и `file-type` сейчас присутствуют только транзитивно (через `@nestjs/platform-express` и `@nestjs/common`); зависимости нужно добавить явно: `pnpm --filter api add multer file-type` и `pnpm --filter api add -D @types/multer`. `file-type` v22 — чистый ESM, Node ≥ 22: совместим с проектом.
- `StorageEngine` реализует `_handleFile(req, file, cb)` и `_removeFile(req, file, cb)`. Multer сам вызывает `_removeFile` для уже сохранённых файлов, если запрос завершился ошибкой (в том числе превышение лимита или обрыв), — это и есть основа требования «нет мусора».
- Контроллер: `@UseInterceptors(FileInterceptor('file', { storage, limits }))`, поле формы — `file`. Авторизация (`JwtAuthGuard`) срабатывает **до** интерцептора, поэтому без JWT тело даже не читается (401). `JwtAuthGuard` не знает про встречу, поэтому владение встречей нужно проверять отдельно, до разбора multipart. Рекомендуется добавить второй guard/интерцептор `MeetingOwnerGuard`, который находит встречу по `:id` и `req.user.id`, кладёт её в `req` и кидает 404 раньше `FileInterceptor` (порядок: `JwtAuthGuard` → `MeetingOwnerGuard` → `FileInterceptor`). Так чужая/несуществующая встреча отвечает 404 без чтения тела и без записи на диск.
- Если клиент отвечает 404/413 раньше, чем дослал тело, Node может закрыть соединение, а XHR в браузере увидит сетевую ошибку вместо ответа (особенно при 413). Для раннего отказа по `Content-Length` стоит читать и отдавать тело (`req.resume()`/`Connection: close`) и проверить это e2e и в браузере; проще всего оставить основным механизмом лимит multer, а `Content-Length`-проверку использовать как ускоритель.

**Лимиты multer:** `fileSize: 500 * 1024 * 1024`, `files: 1`, `fields: 0` (или небольшой лимит), `parts: 2`, `fieldSize` малый, `headerPairs` по умолчанию. Сообщения multer-ошибок (`LIMIT_FILE_SIZE`, `LIMIT_UNEXPECTED_FILE`) нужно перевести в русские через `ExceptionFilter` для `MulterError` либо перехватом в обёртке интерцептора — по умолчанию Nest отдаёт английский текст (например, `File too large`).

## 2. Хранение на диске

- Конфигурация: переменная `FILES_STORAGE_DIR` (по умолчанию `./storage` относительно `apps/api`), папка добавляется в `.gitignore` (и `.prettierignore`/ESLint ignore при необходимости), описывается в `.env.example` и `apps/api/CLAUDE.md`.
- Структура:
  - `<dir>/tmp/<uuid>` — файлы в процессе загрузки;
  - `<dir>/files/<uuid>` — готовые файлы. `tmp` и `files` лежат на **одной файловой системе**, поэтому `fs.rename` атомарен.
- Путь в БД хранить **относительным** (`files/<uuid>`), а не абсолютным: каталог можно перенести/сменить без миграции данных. В `MeetingFile` это поле `storageKey` (или `path` по плану) — абсолютный путь собирается через `path.join(root, key)` + проверка, что результат лежит внутри корня (защита в глубину).
- Исходное имя не участвует в пути вообще — этого достаточно против path traversal. Имя нужно только для отдачи: нормализовать (`path.basename`, удалить управляющие символы, `\r\n`, ограничить длину, например 255 символов) и хранить как есть в `originalName`. В `Content-Disposition` использовать `filename*=UTF-8''<percent-encoded>` плюс ASCII-fallback в `filename=` — иначе кириллические имена ломаются.
- Запись: `pipeline(source, fs.createWriteStream(tmp, { flags: 'wx' }))` — `wx` исключает перезапись существующего файла; права `0o600`. `stream.pipeline` гарантирует закрытие/уничтожение потоков при ошибке.
- На обрыв соединения: у `busboy` приходит событие `close` без `finish`/`error` у файла, у `req` — `aborted`/`close`. Нужно в `_handleFile` слушать `req.on('close')` и, если запись не завершена, уничтожить write-stream и удалить tmp-файл. Это явно покрыть e2e-тестом «прерванная загрузка» (см. §8).
- `fsync` перед `rename` для эталонной надёжности при падении питания не требуется для этой задачи (локальные dev/простое хранилище); можно отметить как будущее улучшение.

## 3. Валидация типа и размера

Проверено экспериментально на синтетических образцах через `file-type` 22.1.1 (`fileTypeFromFile`):

| Формат                             | Определился?                     | Результат `file-type`               |
| ---------------------------------- | -------------------------------- | ----------------------------------- |
| mp4                                | да                               | `video/mp4`                         |
| mov                                | да                               | `video/quicktime` (бренд `qt  `)    |
| m4a                                | да                               | `audio/x-m4a` (бренд `M4A `)        |
| webm                               | да                               | `video/webm`                        |
| mp3 (с ID3 и «голый» с frame sync) | да                               | `audio/mpeg`                        |
| wav                                | да                               | `audio/wav`                         |
| pdf                                | да                               | `application/pdf`                   |
| vtt                                | да                               | `text/vtt` (по сигнатуре `WEBVTT`)  |
| txt, srt                           | **нет**                          | `undefined` — магических байтов нет |
| docx/pptx                          | **не на моих синтетических zip** | `application/zip`                   |

Выводы:

1. **MIME от клиента (`Content-Type` части) — недоверенный**, использовать только как подсказку. В БД писать **определённый сервером** MIME.
2. **Двухэтапная проверка:**
   - Этап 1 (в `StorageEngine`, по первому чанку ≥ 4–12 КБ): быстрый отказ, если сигнатура очевидно не из белого списка. Для бинарных форматов — `fileTypeFromBuffer(firstChunk)`; для OOXML на этом этапе достаточно префикса `PK\x03\x04`.
   - Этап 2 (после записи в tmp, до `rename`): полное определение `fileTypeFromFile(tmpPath)`; для docx/pptx — отдельная проверка архива (см. ниже).
3. **docx/pptx.** `file-type` различает OOXML-подтипы по содержимому `[Content_Types].xml` и именам записей; на моих минимальных тестовых архивах он вернул просто `zip`. Реальные файлы Word/PowerPoint определяются как `docx`/`pptx` по документации библиотеки, но **это нужно подтвердить на настоящих образцах** (положить маленькие `sample.docx`/`sample.pptx` в `apps/api/test/fixtures/`). Если определение неустойчиво — запасной вариант: прочитать центральный каталог zip (`yauzl`/`fflate`, ~без распаковки) и проверить наличие `word/document.xml` (docx) или `ppt/presentation.xml` (pptx). Защита от zip-bomb не нужна, пока файл только хранится и не распаковывается, но стоит зафиксировать, что при последующей обработке (транскрибация/извлечение текста) она понадобится.
4. **txt/vtt/srt** — текстовые форматы: проверка «это текст»: первые ~64 КБ декодируются как строгий UTF-8 (`new TextDecoder('utf-8', { fatal: true })`, BOM допустим) и не содержат NUL-байтов/управляющих символов (кроме `\t\r\n`). Для `.vtt` дополнительно — начинается с `WEBVTT`; для `.srt` — первая непустая строка число, затем строка времени `\d{2}:\d{2}:\d{2},\d{3} --> …` (мягко: достаточно «текст + расширение srt», если строгий формат даст ложные отказы — решить на этапе реализации).
5. **Соответствие расширения типу.** Таблица «расширение → допустимые определённые типы»: `mp4 → video/mp4`, `mov → video/quicktime`, `webm → video/webm`, `mp3 → audio/mpeg`, `m4a → audio/x-m4a` (допустить и `audio/mp4`), `wav → audio/wav`, `pdf → application/pdf`, `docx → docx`, `pptx → pptx`, `txt/vtt/srt → текст`. Переименованный `.exe → .mp4` отклоняется как несоответствие; `.mp4` с содержимым m4a — спорный случай, предлагается отклонять (строгая таблица проще и предсказуемее).
6. **Размер.** Основной механизм — лимит multer (считает фактически принятые байты, не доверяет `Content-Length`). Дополнительно считать размер собственным счётчиком в `StorageEngine` и записывать **фактический** размер из `fs.stat` после записи, а не из заголовков.
7. Реализовать валидатор как чистый модуль `meeting-files/file-validator.ts` (функции без Nest/FS) — его удобно unit-тестировать (фаза 2).

Коды ответов: превышение размера — **413**, неподдерживаемый тип/несоответствие расширению — **415** (или 400 для битого запроса без файла). Все сообщения — на русском.

## 4. Модель данных (Prisma)

```prisma
enum MeetingFileStatus {
  UPLOADED          // на этой итерации единственное значение
  @@map("meeting_file_status")
}

model MeetingFile {
  id           String            @id @default(uuid()) @db.Uuid
  meetingId    String            @unique @map("meeting_id") @db.Uuid
  originalName String            @map("original_name")
  mimeType     String            @map("mime_type")
  size         Int               // 500 МБ < 2 147 483 647; BigInt не сериализуется в JSON
  status       MeetingFileStatus @default(UPLOADED)
  storageKey   String            @map("storage_key")
  uploadedAt   DateTime          @default(now()) @map("uploaded_at")

  @@map("meeting_files")
}
```

- `meetingId` без FK (встречи в памяти) — как решено в плане; индекс создаётся самим `@unique`. Когда встречи переедут в БД, добавляется FK с `onDelete: Cascade` отдельной миграцией (и удаление файла с диска нужно будет привязать к удалению встречи).
- `size`: `Int` достаточно (500 МБ меньше 2 147 483 647 байт), а `BigInt` не сериализуется в JSON без доработки. При росте лимита свыше 2 ГБ тип придётся менять.
- Статус — enum Postgres: добавление значений позже (`PROCESSING`, `PROCESSED`, `FAILED`) делается миграцией `ALTER TYPE … ADD VALUE`, что удовлетворяет требованию PRD «модель допускает добавление статусов».
- Внешний вид ответа API: не отдавать `storageKey`; DTO с полями `id`, `meetingId`, `originalName`, `mimeType`, `size`, `status`, `uploadedAt`.
- e2e-тесты очищают таблицу `users` сами; для `meeting_files` нужно добавить `deleteMany()` в `beforeEach` (и очистку тестового каталога хранилища — отдельная `FILES_STORAGE_DIR` в `test/`, например временная папка `os.tmpdir()` на прогон, задаваемая в `global-setup`).

## 5. Согласованность диска и БД

Принцип: **БД — источник истины о «готовых» файлах, диск пишется первым, любая ошибка = откат диска.**

- **Загрузка (POST):** файл → tmp → валидация → `rename` в `files/` → `prisma.meetingFile.create`. Если `create` упал (в том числе `P2002` — гонка двух одновременных загрузок на одну встречу), удалить `files/<uuid>` и вернуть 409. Если файл у встречи уже есть — POST возвращает **409** («Файл уже загружен, используйте замену»), замена — `PUT`.
- **Замена (PUT):** новый файл → tmp → валидация → `rename` → в одной транзакции обновить запись (`update` на новые `storageKey/originalName/mimeType/size/uploadedAt`) → **после коммита** удалить старый файл. Если сбой до коммита — удалить новый файл, старый и запись не тронуты (требование «при ошибке старый файл остаётся»). Если удаление старого файла после коммита не удалось — не откатывать, а залогировать: остаток подчистит очистка сирот при следующем старте (§7).
- **Удаление (DELETE):** сначала удалить запись в БД, затем файл (best-effort; ошибка `ENOENT` игнорируется). Обратный порядок оставил бы запись, указывающую на несуществующий файл, — это хуже, чем «лишний файл без записи», который подбирает очистка.
- **Скачивание:** если запись есть, а файла нет (`ENOENT`) — 404 с понятным сообщением и логирование, а не 500.
- Операции над одним `meetingId` не сериализуются отдельной блокировкой — достаточно уникального индекса и перечисленных откатов.

## 6. Скачивание

- В Nest: `new StreamableFile(createReadStream(path), { type: mimeType, disposition, length: size })` либо `res.download`. Использовать `@Res({ passthrough: true })`, чтобы сохранялись интерцепторы/фильтры.
- Заголовки: `Content-Type` (определённый сервером MIME), `Content-Length`, `Content-Disposition: attachment; filename="<ascii-fallback>"; filename*=UTF-8''<encoded>`, **`X-Content-Type-Options: nosniff`** (защищает от исполнения загруженного HTML/SVG в браузере; всегда `attachment`, никогда `inline`).
- Поддержка `Range` — вне скоупа (нет плеера, докачки), но `Accept-Ranges` не отдаём.
- **Проблема авторизации.** Скачивание через `<a href>` не добавит заголовок `Authorization`, а токен лежит в `localStorage`. Варианты:
  1. `fetch` с заголовком → `Blob` → `URL.createObjectURL` → клик по ссылке. Просто, но **весь файл (до 500 МБ) грузится в память вкладки** — для больших видео плохо.
  2. **Короткоживущая подписанная ссылка** (рекомендуется): `POST /meetings/:id/file/download-link` (под JWT) возвращает `{ url }` вида `/meetings/:id/file/download?token=<jwt, exp ~60 c, scope=download, meetingId>`; браузер скачивает нативно с потоковой записью на диск и прогрессом. Токен в query-строке попадает в логи — поэтому срок жизни ≤ 1 минуты и узкий scope. Это добавляет один маленький эндпоинт и guard, переиспользуя `AuthTokenService`/`JwtService`.
  3. Cookie-аутентификация — вне скоупа (сессия сейчас в `localStorage`).
  4. File System Access API (`showSaveFilePicker`) — не поддерживается в Firefox/Safari.
     План фазы 3 говорит только про `GET /meetings/:id/file/download`; для варианта 2 в той же фазе добавляется выдача ссылки (или `download` принимает и `Authorization`, и `?token=`). Решение нужно принять до фазы 6 — это единственное место, где исследование предлагает расширить API относительно плана.

## 7. Очистка сирот при старте

- Реализовать `OnApplicationBootstrap` в `MeetingFilesService` (после того как `PrismaModule` готов). Встречи in-memory после рестарта **всегда пусты**, поэтому по сути при каждом старте удаляются все `MeetingFile` и все файлы — это прямое следствие решения из плана (до переноса встреч в БД файлы практически не переживают рестарт API, что противоречит критерию «метаданные и файлы сохраняются после перезапуска API»). **Это противоречие стоит явно зафиксировать:** либо критерий проверяется на уровне «БД и диск пережили рестарт при непустом хранилище встреч», либо перенос встреч в БД делается раньше/вместе с фичей. Для выполнения критерия фазы 1 в e2e достаточно проверить пересоздание модуля при том же `MeetingsService` (или вынести проверку «встреча существует» за интерфейс).
- Алгоритм: (1) удалить всё содержимое `tmp/` (недозаписанные файлы прошлого запуска); (2) загрузить все `MeetingFile` и удалить те, чьей встречи нет (`MeetingsService.findById(meetingId)`), вместе с файлами; (3) пройти `files/` и удалить файлы без записи в БД. Операции идемпотентны, ошибки отдельных файлов логируются и не валят старт.
- В e2e-тестах не включать очистку по умолчанию, иначе она будет сносить данные соседних тестов; запускать её явно или управлять флагом/параметром модуля.
- Для `MeetingsService` потребуется метод, не привязанный к владельцу (`exists(id)`), — текущие методы всегда фильтруют по `ownerId`.

## 8. Таймауты и лимиты тела

Проверено на Node v24.21.0: `http.Server` по умолчанию — `requestTimeout = 300 000 мс` (5 минут на **получение всего запроса**), `headersTimeout = 60 000`, `timeout = 0`, `keepAliveTimeout = 5 000`.

- 500 МБ за 5 минут = ≈ 1,7 МБ/с (≈ 14 Мбит/с). На медленном канале загрузка оборвётся по `requestTimeout`. Рекомендация: в `main.ts` после `app.listen`/через `app.getHttpServer()` задать `requestTimeout = 0` либо значение побольше (например, 30 минут) — нужно именно здесь, не в `setupApp` (его используют e2e), но можно вынести в `configureServer(server)`. `headersTimeout` оставить.
- Глобальные body-парсеры Express/Nest (`json`, `urlencoded`) multipart не затрагивают; отдельного «лимита тела» для multipart нет — работает `limits.fileSize`. JSON-лимит остаётся по умолчанию (100 КБ), что хорошо.
- Reverse-proxy (если появится): `client_max_body_size 520m`, `proxy_request_buffering off`, увеличенные `proxy_read_timeout`/`client_body_timeout`. Сейчас прокси нет, но это нужно учесть в документации по развёртыванию.
- Web (Next.js): загрузка идёт **напрямую в API** (`NEXT_PUBLIC_API_URL`), минуя Next.js, поэтому лимитов тела Next (в т.ч. `proxyClientMaxBodySize`/server actions 1 МБ) не затрагивается. Не использовать Server Actions и route handlers как прокси для файла.
- Диск: перед приёмом не проверяем свободное место (квоты вне скоупа); при `ENOSPC` — 507/500 с русским сообщением и откат tmp.

## 9. CORS

`enableCors({ origin: WEB_ORIGIN })` уже включён. Для XHR с `Authorization` и multipart браузер шлёт preflight (`OPTIONS`), который Nest обрабатывает автоматически (заголовки по умолчанию: `Access-Control-Allow-Headers` отражает запрошенные). Проверить на практике:

- Для скачивания по ссылке с токеном CORS не нужен (навигация, не XHR).
- Если фронт будет читать `Content-Disposition` из XHR/fetch (вариант 1 из §6), его нужно добавить в `exposedHeaders`.
- Preflight для PUT/DELETE — методы по умолчанию в `enableCors` включают `PUT`, `DELETE`.
- Ошибки 413/401 без CORS-заголовков браузер превратит в «Network Error»; Nest добавляет CORS-заголовки на все ответы через middleware, но при принудительном закрытии сокета (ранний отказ до чтения тела) заголовков не будет — это тот же риск, что в §1, проверяется в браузере через Playwright MCP.

## 10. Клиент (web)

- **Загрузка:** `XMLHttpRequest` с `xhr.upload.onprogress` (проценты и, при желании, скорость), `xhr.abort()` для отмены, `setRequestHeader('Authorization', …)`; тело — `FormData` (поле `file`). `fetch` не подходит из-за отсутствия прогресса отправки. Обёртка `uploadMeetingFile(meetingId, file, { onProgress, signal })` лежит в `src/lib/api.ts` (единственная точка обращения к API по соглашению проекта), с тем же сбросом сессии при 401. `Content-Type` вручную не задавать — браузер поставит `multipart/form-data` с boundary.
- **Клиентская валидация:** чистый модуль `src/lib/meeting-file.ts` — таблица допустимых расширений и MIME, лимит 500 МБ (константа, одинаковая с сервером; значение дублируется осознанно — общего пакета в монорепозитории нет, выносить в shared-пакет для одной константы избыточно), `formatFileSize`, `validateFile(file)` → русское сообщение или `null`. На клиенте проверяются расширение + `file.type` как подсказка (у `.mov`, `.m4a`, `.srt`, `.vtt` `file.type` в разных ОС пустой/разный → не отклонять по пустому MIME). Источник истины — сервер.
- **Зона загрузки (HeroUI v3):** в HeroUI v3 нет готового Dropzone — собирается из `Card`/`Button` + скрытого `<input type="file" accept="…">`. Доступность: зона — `<label>` или кнопка (`role="button"`, фокус, `Enter`/`Space` открывают диалог), `onDragOver/onDragEnter/onDragLeave/onDrop` только для визуальной подсветки и приёма файла; `aria-describedby` на подсказку о форматах, прогресс — `ProgressBar` с `aria-valuenow`, ошибки в `role="alert"`/`aria-live="polite"`; цель касания ≥ 44 px (`min-h-11`), текст вторичный — `text-muted`; по правилам проекта «при отправке — `isPending`», пустое/ошибка/загрузка — отдельные состояния. Учесть `prefers-reduced-motion`.
- **Состояния:** `idle → dragging → uploading(progress) → success | error(retry)`; при ошибке показывать сообщение с сервера (русское) или общее «Не удалось загрузить файл. Проверьте соединение и повторите»; повтор — тот же `File`, новый XHR. Отмена — `abort()` (сервер удалит tmp-файл по обрыву).
- **Замена и удаление:** замена — тот же компонент в режиме `PUT`, старая карточка остаётся до успеха; удаление — модальное окно подтверждения HeroUI (`Modal`), после успеха возвращается зона загрузки.
- **Список встреч:** поле `hasFile: boolean` из `GET /meetings` (фаза 4) → иконка/`Chip` «Есть файл» с текстовой альтернативой (не только цвет/иконка).
- **Индикатор в API:** признак считается одним запросом `meetingFile.findMany({ where: { meetingId: { in: ids } }, select: { meetingId: true } })`, а не N+1.
- **Тесты:** unit для `validateFile`/`formatFileSize` (в web нет тестового раннера — для фазы 5 «unit-тесты клиентской валидации» нужно добавить `vitest` в `apps/web` и скрипт `test`, обновить `pnpm test` в корне и `CLAUDE.md`); сценарии UI — через Playwright MCP по соглашению проекта (скриншоты, мобильная ширина, клавиатура, тёмная тема, скилл `ui-ux-pro-max`).

## 11. Архитектура модуля на API

Соответствие соглашениям `apps/api/CLAUDE.md`: модули по доменам, контроллер + сервис + DTO + модуль в одной папке; CQRS используется только в `auth`, для файлов — обычные контроллер и сервис (как в `users`/`meetings`).

```
apps/api/src/meeting-files/
  meeting-files.module.ts       # импортирует MeetingsModule (экспортирует MeetingsService) и PrismaModule
  meeting-files.controller.ts   # POST/PUT/GET/DELETE /meetings/:id/file, GET …/download
  meeting-files.service.ts      # метаданные в Prisma, откат диска, очистка сирот
  meeting-file.storage.ts       # multer StorageEngine (tmp-запись, peek первого чанка, cleanup)
  meeting-file.validator.ts     # чистые функции: тип, расширение, текст, имя
  meeting-file.config.ts        # FILES_STORAGE_DIR, MAX_FILE_SIZE, разрешённые типы
  meeting-owner.guard.ts        # 404 для чужой/несуществующей встречи до чтения тела
  meeting-files.dto.ts          # MeetingFileDto, toDto()
```

- Эндпоинты — под `meetings/:id/file`, но контроллер живёт в новом модуле (`@Controller('meetings/:id/file')`), чтобы не раздувать `MeetingsController`. Изменение `GET /meetings`/`GET /meetings/:id` (`hasFile`) делается в `MeetingsController` через `MeetingFilesService` — следить за циклическими зависимостями модулей (файловый модуль зависит от встреч; встречи — только от «читающего» метода файлов; если возникнет цикл, вынести признак в отдельный запрос в контроллере либо использовать `forwardRef`).
- `MeetingsService` пока in-memory: при переходе на БД менять нужно только его; файловый модуль общается с ним через `findOneByOwner` и `exists`.
- Обработка ошибок: `HttpException` с русскими сообщениями; глобальный фильтр для `MulterError`.

## 12. Тестирование

- **Unit (vitest):** валидатор типа/расширения/текста (таблица кейсов), нормализация имени, сервис замены/удаления с мок-Prisma и временной директорией (`fs.mkdtemp`) — в том числе «ошибка в транзакции → новый файл удалён, старый на месте»; подсчёт `hasFile`; очистка сирот на временном каталоге.
- **e2e (supertest):** `request.post(...).attach('file', buffer, 'name.mp4')` — для успешных кейсов; для лимита генерировать файл > 500 МБ **без выделения памяти** нельзя через `attach(Buffer)` — использовать поток/`Readable`, либо понизить лимит через конфиг в тестовом окружении (например, `MAX_FILE_SIZE_BYTES` из окружения, 1 МБ в тесте). Рекомендуется сделать лимит конфигурируемым внутренне (константа по умолчанию 500 МБ, переопределяется только в тестах), а один-два теста гонять на настоящем значении через стриминговый генератор. Прерванная загрузка: открыть сырой TCP/`http.request`, послать часть тела и `req.destroy()`, затем дождаться и проверить, что `tmp/` пуст, а в БД нет записи.
- **Контрольная сумма скачивания:** сравнить `sha256` загруженного буфера и скачанного (`crypto.createHash`).
- **Фикстуры:** маленькие настоящие образцы (`.docx`, `.pptx`, `.pdf`, `.mp3`, `.mp4`, `.wav`, `.txt`, `.vtt`, `.srt`) в `apps/api/test/fixtures/`; их суммарный размер — десятки КБ, коммитятся. Исключить из Prettier (`.prettierignore`), чтобы бинарные/текстовые образцы не переформатировались хуком.
- **Изоляция:** отдельная временная `FILES_STORAGE_DIR` на прогон; `beforeEach` чистит `meeting_files` и каталог.

## 13. Безопасность (сводка)

| Риск                                     | Мера                                                                                                 |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Path traversal                           | имя на диске = `randomUUID()`; исходное имя только в БД; проверка `resolved.startsWith(root)`        |
| Подмена расширения/MIME                  | сервер определяет тип по содержимому, сверяет с расширением; клиентский MIME не доверяется           |
| XSS через скачанный файл (HTML/SVG)      | всегда `attachment`, `nosniff`, MIME из белого списка; HTML/SVG/JS вообще не принимаются             |
| Заголовок `Content-Disposition` инъекция | кодирование `filename*`, вырезание `\r\n`/кавычек, ограничение длины                                 |
| Исчерпание диска/памяти                  | потоковая запись, лимит 500 МБ, один файл на встречу, `fields: 0`; квоты вне скоупа                  |
| Висящие tmp-файлы                        | очистка при обрыве и при старте                                                                      |
| Доступ к чужим файлам                    | `JwtAuthGuard` + `MeetingOwnerGuard` (404, не 403 — не раскрываем существование)                     |
| Утечка токена в ссылке скачивания        | TTL ≈ 60 с, scope=download, привязка к `meetingId`                                                   |
| Zip-bomb / вредоносное содержимое        | не распаковываем и не исполняем; антивирус вне скоупа (зафиксировать как риск для будущей обработки) |

## 14. Открытые вопросы и риски

1. **Критерий «файлы переживают рестарт» vs. встречи в памяти** (§7): после рестарта встреч нет, значит, файлы по решению плана будут удалены очисткой. Нужно подтвердить трактовку критерия или перенести встречи в БД раньше.
2. **Способ скачивания** (§6): подписанная ссылка (рекомендуется, +1 небольшой эндпоинт) или blob в памяти. Решение влияет на фазы 3 и 6.
3. **Распознавание docx/pptx** (§3): подтвердить `file-type` на реальных файлах или добавить проверку центрального каталога zip.
4. **Ранний отказ и XHR** (§1, §9): проверить, что ответ 404/413 доходит до браузера (а не «Network Error») при отказе до дочитывания тела.
5. **Тестовый раннер в `apps/web`** (§10): его сейчас нет, а фаза 5 требует unit-тесты — нужно добавить `vitest` и обновить команды/документацию.
6. **`requestTimeout`** (§8): значение зависит от ожидаемого канала пользователей; предложено отключить/увеличить.
7. **`.mp4` с аудио-содержимым и прочие пограничные соответствия** (§3, п. 5): строгая таблица может давать ложные отказы — собрать реальные образцы от пользователей до финализации.

## 15. Рекомендуемый порядок работ по фазам

- **Фаза 1:** модель + миграция, `FILES_STORAGE_DIR`, модуль, `StorageEngine` (пока с записью в tmp → rename без глубокой валидации), `MeetingOwnerGuard`, `POST`/`GET`. Подтвердить трактовку рестарта (§14.1).
- **Фаза 2:** лимиты, валидатор (двухэтапный), русские ошибки через фильтр, очистка при обрыве, фикстуры, тесты; проверить `requestTimeout`.
- **Фаза 3:** download (+ ссылка с токеном, если принято), `PUT` с откатом, `DELETE`.
- **Фаза 4:** `hasFile` в списке/деталях одним запросом, очистка сирот на старте.
- **Фаза 5–6:** `vitest` в web, XHR-загрузка, зона загрузки, карточка, замена, удаление, индикатор; визуальная проверка через Playwright MCP.
- **Фаза 7:** документация (`CLAUDE.md` ×3, `README.md`, `.env.example`: `FILES_STORAGE_DIR`, при необходимости `MAX_FILE_SIZE_BYTES`/`DOWNLOAD_LINK_TTL`), финальный прогон `pnpm format/lint/typecheck/test` и `pnpm --filter api test:e2e`.
