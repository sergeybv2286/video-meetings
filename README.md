# video-meetings

Монорепозиторий (pnpm workspaces):

| Пакет | Стек            | Путь       | Порт |
| ----- | --------------- | ---------- | ---- |
| `web` | Next.js, HeroUI | `apps/web` | 3000 |
| `api` | NestJS          | `apps/api` | 3001 |

## Старт

```bash
pnpm install
docker compose up -d   # Postgres на порту 5432
pnpm dev               # web + api параллельно
```

## База данных

Postgres 17 поднимается через `docker-compose.yml` (контейнер `video-meetings-postgres`, том `postgres_data`).
Параметры по умолчанию: пользователь, пароль и база `video_meetings`, порт `5432`; переопределяются через `.env` в корне (см. `.env.example`).

- `docker compose up -d` — запустить, `docker compose down` — остановить (данные сохраняются), `docker compose down -v` — остановить и удалить данные
- Строка подключения: `postgresql://video_meetings:video_meetings@localhost:5432/video_meetings`

API работает с БД через Prisma (`apps/api/prisma/schema.prisma`): в Postgres хранятся пользователи и метаданные файлов встреч (таблица `meeting_files`). Сами встречи пока хранятся в памяти API и теряются при перезапуске (см. «Файлы встреч»).

- `pnpm --filter api db:migrate` — создать и применить миграцию в dev-БД (после изменения схемы)
- `pnpm --filter api db:deploy` — применить существующие миграции
- Prisma Client генерируется в `apps/api/src/generated` (в git не хранится) автоматически при `pnpm install`; вручную — `pnpm --filter api db:generate`
- Строка подключения — `DATABASE_URL` (по умолчанию как выше)
- e2e-тесты используют отдельную БД `video_meetings_test` (создаётся и мигрируется автоматически, нужен запущенный Postgres)

## Профиль

- **Интерфейс:** в шапке главной — заглушка с инициалами, имя и email со ссылкой на профиль. Страница `/profile` показывает имя, email и заглушку с инициалами (по имени, а без имени — по email), кнопка «Редактировать» ведёт на `/profile/edit`.
- **Редактирование:** на `/profile/edit` форма имени и email (`PATCH /users/me`): после сохранения появляется подтверждение, очистка имени сбрасывает его (везде показывается email), занятый email даёт сообщение «Этот email уже занят». Изменения видны в профиле и шапке без повторного входа. Неавторизованного обе страницы перенаправляют на вход.
- **Пока нет:** смена пароля и удаление аккаунта в интерфейсе (есть только в API: `PUT /users/me/password`, `DELETE /users/me`) и аватар-изображение (вместо него заглушка с инициалами).

## Файлы встреч

К своей встрече можно прикрепить один файл: **mp4, mov, webm, mp3, m4a, wav, pdf, docx, pptx, txt, vtt, srt**, до **500 МБ**. Тип проверяется на сервере по содержимому, а не только по расширению; ошибки — на русском.

- **Интерфейс:** страница встречи `/meetings/<id>` (ссылка из списка встреч): загрузка выбором или перетаскиванием, прогресс, карточка файла, скачивание, замена, удаление с подтверждением. В списке встреч у встреч с файлом метка «Есть файл». Работает на мобильной ширине и с клавиатуры.
- **API** (все маршруты под JWT, доступ только владельцу встречи, для чужой или несуществующей встречи — 404):

  | Метод и путь                      | Что делает                                                    |
  | --------------------------------- | ------------------------------------------------------------- |
  | `POST /meetings/:id/file`         | загрузка (multipart, поле `file`); 409, если файл уже есть    |
  | `PUT /meetings/:id/file`          | замена файла (старый удаляется, при сбое остаётся нетронутым) |
  | `GET /meetings/:id/file`          | метаданные: имя, тип, размер, статус, дата загрузки           |
  | `GET /meetings/:id/file/download` | скачивание (потоком, с исходным именем)                       |
  | `DELETE /meetings/:id/file`       | удаление с диска и из метаданных (204)                        |

  Также `hasFile` есть в ответах `GET /meetings`, `GET /meetings/:id` и `POST /meetings`. Подробности — в `apps/api/CLAUDE.md`.

- **Хранение:** файлы лежат на диске в `FILES_STORAGE_DIR` (по умолчанию `apps/api/storage`, в git не попадает), метаданные — в Postgres. Лимит размера — `MEETING_FILE_MAX_SIZE` (байты). Переменные — в `.env.example`.
- **Ограничения:**
  - Встречи хранятся в памяти API, поэтому после перезапуска они пропадают. Чтобы не копились «осиротевшие» данные, при старте API удаляет записи и файлы, у которых нет встречи, и хвосты незавершённых загрузок. То есть файлы **не переживают перезапуск API**, пока встречи не перенесены в БД (отдельная задача).
  - Один файл на встречу; без докачки и встроенного плеера: файл только скачивается.
  - Скачивание в браузере держит файл целиком в памяти (до 500 МБ).

## Тесты

| Команда                        | Что запускает                                                                       | Нужен Postgres |
| ------------------------------ | ----------------------------------------------------------------------------------- | -------------- |
| `pnpm test`                    | unit-тесты пакетов (`apps/api/src/**/*.spec.ts`, `apps/web/src/**/*.test.{ts,tsx}`) | нет            |
| `pnpm --filter api test:e2e`   | e2e API (`apps/api/test/*.e2e-spec.ts`: auth, users, meetings, файлы встреч)        | да             |
| `pnpm --filter api test:watch` | unit-тесты API в watch-режиме                                                       | нет            |
| `pnpm --filter api test:cov`   | unit-тесты API с покрытием                                                          | нет            |

Для e2e сначала запустите Postgres: `docker compose up -d`. Тесты работают с отдельной БД `video_meetings_test` (адрес переопределяется через `TEST_DATABASE_URL`): перед прогоном `test/global-setup.ts` применяет к ней миграции, файлы идут последовательно, а таблицы `users` и `meeting_files` тесты очищают сами (файлы e2e — во временной папке), dev-данные не затрагиваются. Один файл: `pnpm --filter api test:e2e -- test/users.e2e-spec.ts`.

Перед завершением работы прогоните всё: `pnpm format && pnpm lint && pnpm typecheck && pnpm test && pnpm --filter api test:e2e`.

## Скрипты (из корня)

- `pnpm dev` / `dev:web` / `dev:api` — режим разработки
- `pnpm build` / `build:web` / `build:api` — сборка
- `pnpm lint` — линтинг (ESLint в web, oxlint в api)
- `pnpm test` — unit-тесты всех пакетов (e2e API запускаются отдельно, см. «Тесты»)
- `pnpm typecheck` — проверка типов
- `pnpm format` / `format:check` — Prettier для всего репозитория
- Git-хук `pre-commit` (Husky, `.husky/pre-commit`) перед каждым коммитом запускает `pnpm lint` и `pnpm test`; устанавливается автоматически через `prepare` при `pnpm install`. Обойти в крайнем случае: `git commit --no-verify`
